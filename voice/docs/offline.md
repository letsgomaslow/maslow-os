# Fully offline workspace

Fully offline mode runs a dedicated Ollama service, Hermes coordinators, coding children and supported applications inside one Linux bubblewrap namespace per workspace. It never reuses the desktop's Ollama port or LM Studio process. LM Studio belongs to Server mode. Model selection alone is not readiness: startup checks the dedicated service's model inventory, rejects remote model metadata, then completes actual inference with every selected model inside the disconnected namespace. Missing models, unsupported isolation or failed inference stop startup without a cloud fallback.

## Boundary

`offline.py` creates an empty filesystem root with `bwrap --unshare-all --cap-drop ALL --clearenv`. This includes a mandatory network namespace, PID namespace and IPC namespace. There is no `--try` isolation and no fallback to an ordinary host process. Loopback services are private to the namespace. The mounted project is a copy with distinct writable inodes; the original project is never mounted. The namespace has its own writable home, temporary directory, runtime directory, application profiles and browser profile. Installed system software under `/usr`, standard library directories and the exact packaged `/opt/hermes-agent`, `/opt/claude-code` and `/opt/google/chrome` trees is read-only; only selected non-secret system font, certificate, loader and timezone data is exposed from `/etc`. No host root, user home, `/run`, `/tmp`, D-Bus, PipeWire, SSH agent, browser profile or Chrome debugging socket is mounted.

Project and model-folder validation rejects symbolic links, sockets, FIFOs and device files. Ancestor directories are opened without following symbolic links. This intentionally excludes projects containing symlinked dependency directories until the user prepares a regular-file copy. No host watcher, desktop launcher, shell profile, user service or autostart location receives agent writes. Installed tools must be available in the isolated system PATH; executables and virtual environments installed only under the user's personal home are unavailable. CPU inference is supported by the filesystem boundary; GPU device passthrough is not implemented.

The worker speaks bounded JSON messages over inherited stdin/stdout. Model HTTP requests are restricted to dedicated local inference operations. Hermes requests are restricted to the coordinator endpoints started by that worker. Subprocesses do not inherit the control streams. All worker output and tool requests remain untrusted data: the daemon's tool handler must bind requests to the originating offline project and verify the task session. A token alone cannot authorize a request for an online task or another project. Export must never be exposed through this agent tool bridge.

## Visible applications

`OfflineRuntime.open_display()` starts a new trusted Weston compositor as a normal nested Wayland window. It uses a private home, configuration and runtime directory, the kiosk shell, no Xwayland and no configured host launchers or autostart clients. The isolated application receives only this newly created compositor socket. It cannot reach the original desktop compositor socket. The parent display connection stays inside trusted Weston, outside the executor. Weston forwards display and input for its own window; no clipboard bridge, screen-capture bridge, shared folder or D-Bus forwarding is configured.

This makes Weston and its Wayland parser part of the trusted boundary; it is not a claim that a compositor vulnerability is impossible. Closing/stopping the workspace kills its namespace and closes the nested compositor. The actual window must be checked in a Linux Wayland desktop before claiming native visual acceptance. Headless container tests establish namespace behavior, not a native desktop session or successful application use.

Call `open_display()` before `start(project=...)` when visible apps are required. Supported names are `terminal`, `files`, `editor` and `browser`, with fixed installed executable choices. `open_url()` accepts private localhost previews and project files. Applications cannot fetch websites or install packages from the internet in fully offline mode. Launch responses report that a process started; they do not establish that the app completed the user's work.

## Integration API

- `OfflineRuntime(directory, settings, tool_handler=None)` owns one project workspace. `settings` may be the Settings object or a settings dictionary.
- `await runtime.open_display()` prepares the optional trusted display bridge.
- `await runtime.start(project=host_project)` copies the selected project and verifies dedicated model readiness. Selecting a different project while this runtime is active fails. A stopped runtime retains its private copy when restarted with the same project.
- `await runtime.model_request(path, payload=None)` returns JSON from the namespace's Ollama service. It never contacts the host model service.
- `await runtime.spawn(argv, cwd='/project', env={}, input=None, timeout=120)` runs and waits for a bounded command, returning `returncode`, `stdout`, and `stderr`. Output and duration are bounded; command descendants are killed on failure or timeout. The cwd must remain inside `/project`. Reserved environment fields cannot override the isolated home, IPC or system PATH.
- `await runtime.launch_hermes(configuration, plugin_path, environment)` creates a private profile and returns `endpoint` and `token`. Construct `HermesClient(endpoint, token, request=runtime.hermes_request)` so requests cross the data bridge. Status polling is supported; direct host SSE connections are not.
- `await runtime.open_application(name)` and `await runtime.open_url(url)` launch inside the isolated namespace with the prepared nested display.
- `await runtime.stop()` terminates execution before file review/export.

Trusted speech capture/playback may run outside this namespace with verified local speech assets. Only text/structured intent crosses into execution. Do not expose raw PipeWire, audio-server, D-Bus or host display-control sockets to executors.

## Review and export

The private snapshot survives stopping. `runtime.workspace.review()` requires stopped execution and returns a digest plus a list of changed paths with `add`, `modify` or `delete` actions. The current desktop displays these paths and actions; choosing **Export reviewed changes** explicitly exports that entire displayed list. It does not yet provide a content diff or per-file selection. The underlying `runtime.workspace.export(review_digest, selected_paths)` API also supports a subset of changed paths. It requires the same reviewed snapshot digest, rejects paths outside the changed-file list, validates the stopped snapshot again, and compares each selected original file to its initial snapshot fingerprint. A source edit causes a conflict before any selected file is written. Unselected files remain untouched. Each written file uses a temporary file and atomic replacement; a multi-file export is not one filesystem transaction, so an I/O failure can leave a partial export and requires another review. Empty-directory-only changes are not exported.

Do not automatically export files after task completion. Export is a trusted desktop action, separate from model and tool permissions. Changes to an open source project can still race ordinary host editors during export; pause editing while applying reviewed files. Private workspaces retain their original source identity and baseline metadata outside all executor mounts. Restarting with the same selected source restores that private copy and its original conflict baseline; keep these files for recovery before deleting state.

## Validation evidence and remaining gates

The focused tests cover snapshot inode separation, regular-file enforcement, unsafe ancestors, review expiry, explicit selected-file export, source conflicts, mandatory isolation flags, forbidden host IPC environment and rejection of unsupported platforms/LM Studio. A real Linux ARM container test also starts bubblewrap and proves that a child process cannot connect to a host-loopback listener or an external IP, see a host Unix socket or secret file, or inherit an unrelated secret environment variable; its descendant can write only the private project. This is Linux namespace proof inside Docker, not macOS sandbox enforcement or Lenovo hardware evidence.

Run `PYTHONPATH=voice python3 -m unittest discover -s voice/tests -p test_offline.py -v`. The real boundary test skips on non-Linux systems and when a container/kernel cannot create namespaces. Set `MASLOW_REQUIRE_ISOLATION_TEST=1` in Linux acceptance to make unavailable namespaces a failure. The existing x86 Docker image under Apple ARM emulation could not create namespaces. The smoke passed in a disposable native ARM Python/Alpine container with bubblewrap; no product fallback was added.

The installed x86 QEMU/TCG guest also passed actual downloaded `qwen2.5:0.5b` inference in the disconnected namespace, nested Weston/Foot rendering and a typed `pwd` response, a private child write and explicit reviewed export. See the [implementation handoff](../../docs/handoffs/2026-09-13-maslow-voice-implementation.md) for exact package/model evidence and the memory-constrained failure that preceded it. Remaining acceptance includes Hermes/coder model execution inside the namespace, sustained application interaction, the complete speech-to-task-to-reviewed-export flow and final Lenovo behavior. Tests using mocked model responses do not satisfy those remaining gates.
