# LiveKit native audio recovery

This continues the [installed handoff checkpoint](2026-09-14-livekit-installed-handoff.md). The scope is real spoken LiveKit Expressive conversation and Hermes delegation in the existing installed Maslow AI-OS guest before Lenovo testing. No ISO rebuild, UTM, signing, publication, OTA or Lenovo change is included.

## Diagnosis and retained failures

The original provider transported local microphone audio through a published LiveKit room into another local AgentSession, then returned synthesized audio through the room to the same computer. In this x86 QEMU/TCG guest, serialized native APM processing plus the room's awaited audio submission could not consistently keep up with 20 ms capture. The full-room profile measured median capture submission of 16.393 ms and median APM work of 8.245 ms. Profiling overhead and emulated rendering contention limit the interpretation; these are not physical laptop timings.

Increasing QEMU's translation cache from 64 to 256 MiB reduced translation-cache flushes, and limiting the software compositor to two guest CPUs reduced its measured CPU use from about 694% to 194%. Quickshell used its software renderer and the actual Voice panel was inspected in QMP screenshots. These are temporary QA resource controls, not production configuration or UI performance acceptance. Neither they nor a separate 40 ms audio-submission experiment passed the original silent-intake gate with the room provider. All failures remain saved independently.

The direct-audio experiment uses the SDK's supported custom AgentSession input/output interface while retaining LiveKit cloud inference, Expressive mode, the same models/voice, strict task tool, native PortAudio, and WebRTC echo/noise processing at 48 kHz. It removes the local audio trip through two room participants. The microphone then sustained about 50 frames per second without drops.

Two further issues emerged during the experiment:

- The first output adapter trusted a virtual ALSA/PortAudio latency value of about 89,478 seconds. An independent zero-audio driver probe reproduced this impossible value. Upstream ALSA backend arithmetic can produce this unsigned-underflow pattern; the exact virtual-device negotiation that triggers it was not established. The original room provider did not use this timing metadata. The correction uses exact consumed-sample counts and a bounded device-latency estimate; malformed metadata cannot hold completion for hours. A 985-sample regression demonstrates why integer millisecond rounding is insufficient.
- With AgentSession's default three-second AEC warmup, the overlapping question was transcribed as “While” and “for packing lightly.” SDK 1.8.1 deliberately replaces STT-bound audio with silence in that first speaking interval. Explicit zero warmup preserves input while retaining Maslow's local APM. The next otherwise-identical run heard the complete question and replied while Hermes worked. It interrupted the acknowledgment before an observed speaking state, so that run alone does not establish every timing of interruption after playback has begun. Physical speaker echo remains a separate check.

One diagnostic helper originally divided a request phase that included 15 seconds of injection plus 30 seconds of waiting by only 30 seconds. Its reported 44.63 fps is invalid; elapsed-time-corrected throughput was about 29.5 fps. The original result and a caveat file are retained, and the future helper was corrected. It was not rerun and is not acceptance evidence.
