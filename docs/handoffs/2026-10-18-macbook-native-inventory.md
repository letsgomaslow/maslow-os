# Native MacBook inventory and first reproduced performance symptom — October 18, 2026

## Scope and inputs

This session ran directly on the installed 2012 15-inch Retina MacBook Pro (`MacBookPro10,1`), confirmed via DMI product name and a native Wayland session — not a VM, not the build Mac. This is the first directly observed native inventory and the first reproduced symptom called for as the next action in [the native development handoff](2026-10-18-macbook-native-development.md).

No source was changed, no package was installed or updated, no ISO/packaging work occurred. All diagnostics were read-only except one temporary nouveau GPU performance-level override via `/sys/kernel/debug/dri/0000:01:00.0/pstate`, reverted to `AC` before this entry was written. That override is runtime-only debugfs state; it is not written to any file, service, or config, so a reboot alone fully clears it with no residual effect. Every `sudo`-gated command was run by the user at the physical keyboard, per this repository's own privilege-escalation rule (`sudo` in a visible terminal; model-side tooling cannot supply a login password).

## Results observed in this run

- Baseline: kernel `7.2.8-8-omarchy-bore`; installed package set matches the frozen candidate table (Hub 2.0.3-2, Voice 0.1.5-47, Hermes 0.22.2-4, Qt 6.12); zero failed systemd units (system and user); Wi-Fi associated via the Broadcom `wl` DKMS module. Boot timing 22.2s total (firmware+loader+kernel+userspace); nothing anomalous in `systemd-analyze blame`.
- CPU (i7-3615QM) ran at 3.0–3.3GHz under `schedutil` throughout; no thermal-throttle messages in `dmesg`. CPU is not implicated in the reported slowness.
- **Confirmed root cause of reported sluggishness**: `apple_gmux` currently routes the internal Retina panel (`eDP-1`) to the discrete NVIDIA GT650M via `nouveau`, not to Intel HD4000 (`i915`, which sits idle/runtime-suspended and drives no output). Nouveau parks this GPU at `core 405MHz / memory 680MHz` (its `AC` state) against an available maximum of `core 900MHz / memory 5016MHz` (state `0f`) — roughly 13% of available memory bandwidth, the dominant cost for compositing a 2880×1800 panel. A live, reproducible kernel fault ties this directly to real compositor load: repeated `nouveau 0000:01:00.0: gr: DATA_ERROR 00000004 [INVALID_VALUE] ... chrome[9725] ... class a097 mthd 0804` entries, correlated to Chrome's GPU process (launched with `--render-node-override=/dev/dri/renderD128`, nouveau's render node).
- Live reversible test: forcing nouveau to pstate `0f` produced an immediate, user-confirmed smoothness improvement ("way smoother"), at the cost of fans climbing from an idle ~2600–2800 RPM to 4722/5099 RPM (near their 5499/5940 RPM maximums) and GPU-area temperatures rising to ~74–78°C — within the sensors' normal range, no throttle/shutdown indication, but not free. The override was reverted to `AC` afterward; nothing was left pinned. This confirms the diagnosis; it is not itself a sustainable fix, since it trades continuous battery/heat/fan noise for bandwidth regardless of actual load.
- Suspend/resume: one short (~15s) cycle via `systemctl suspend` passed cleanly. Kernel log shows `PM: suspend entry (deep)` / `PM: suspend exit` with no device failing to suspend or resume; Wi-Fi reassociated automatically; system clock/uptime stayed coherent. The only resume-time GPU log line was a routine nouveau VBIOS replay trace (`devinit: 0x0000644c[0]: script needs OR link`), not an error, and the display returned correctly per direct visual confirmation from the user. A longer overnight or lid-closed suspend was not tested and remains open.
- Audio: Built-in Analog Stereo sink and source both present, default, and at sane volumes under PipeWire/WirePlumber. FaceTime HD camera enumerated on `/dev/video0`/`/dev/video1` and visible to PipeWire as a video source. No defect found.
- Input: Apple Internal Keyboard/Trackpad recognized via the `bcm5974` driver, the correct driver generation for this hardware. No defect found; gesture quality was not separately scored.
- Thunderbolt: `bolt` service active, no enrolled devices — expected, since none were connected during this session.
- Battery (hardware fact, not a software defect): `upower` reports 49.5% of design capacity remaining (45.9Wh of 92.6Wh design) after 1187 charge cycles, consistent with a 14-year-old original battery. A charge-limiting threshold (75–80%) is already active and protecting what capacity remains. This affects on-battery runtime independent of the GPU finding above; only physical battery replacement addresses it.
- Secondary, unresolved findings: `fstrim.timer` is disabled on the SSD-backed LUKS+btrfs root despite `ssd`-aware mount options, so periodic TRIM never runs; and `vm.swappiness` is set to `150` against a zram+disk swap setup. Neither is confirmed as an intended default for this hardware class.

## Remaining gates

1. Decide and implement the actual fix for the GPU finding — most likely switching the panel to Intel HD4000 at boot via `apple_gmux`, rather than leaving nouveau pinned to a high pstate continuously. This needs a boot-time change, not a hot in-session mux switch: switching the active display's GPU out from under a running Wayland compositor risks crashing the session. Not attempted in this run.
2. Confirm whether `fstrim.timer` disabled and `vm.swappiness=150` are intended Maslow defaults for this hardware class or unintentional; fix in the owning repository if not.
3. Test an actual longer (overnight or lid-closed) suspend cycle; only a 15-second wake test has been directly observed so far.
4. Voice/provider audio (microphone capture, a heard spoken response, real sign-in) and agent task delivery remain untested in this session, consistent with every prior handoff's evidence boundary.
5. Battery replacement is a hardware decision for the user, not a source change.

Next action: take item 1 (Intel-GPU boot-time switch) to the owning `maslow-os` desktop/boot configuration, prototype it as a reversible, scoped change, and verify visually on this same hardware before considering it fixed. Do not infer this result for the Lenovo target or any VM; the historical Qt/startup continuity gates recorded in prior handoffs remain separately open and are unaffected by this entry.
