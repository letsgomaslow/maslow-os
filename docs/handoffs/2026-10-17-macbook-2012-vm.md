## Results observed in this run

- Passed: installed-disk UEFI boot, SSH, branded SDDM login screen, QMP virtual-keyboard fixture login and actual user-owned Hyprland/Quickshell session.
- Passed visually after startup delay: branded desktop/bar, foot terminal, older integrated AI onboarding panel and Chrome rendering a local test page. Inspected `greeter.png`, `apps-progress.png`, `terminal.png` and `browser-final.png`; the earlier black frames were startup observations, not final desktop failure.
- Passed CLI startup: Codex `0.152.0`, Claude Code `2.1.252`, Hermes Agent `0.21.0`; version commands only, no authentication, model inference or agent task.
- Guest reports kernel `7.2.3-arch1-2`, runtime/settings `4.0.0.r2068.gde97121-1`, Btrfs root and no failed system/user units in the captured probes. No journal matches for illegal instruction, invalid opcode or segfault in the captured initial/session checks.
- Not passed: shell IPC responsiveness. `omarchy-shell shell ping` reported not responding; Hyprland IPC timed out intermittently while applications eventually rendered. No assertion about physical laptop performance follows from TCG timings.
- Visual limitation: old onboarding content clips in its smaller tiled allocation; startup update/keybinding notifications overlap its header. This is evidence for the September image, not the accepted Hub 2 design.
- Virtual graphics warnings: Chrome VA-API/command-buffer failures occurred before it rendered the local page. Audio has only Dummy Output because this VM profile exposes no sound hardware. Wi-Fi, Bluetooth, camera, actual audio and external networking were not tested.
- QEMU warns that TCG cannot provide the requested `tsc-deadline` CPU timer feature. The named CPU profile is an approximation.
- Standalone `maslow-hub` and `maslow-voice` packages are absent. Current Hub 2.0.3/Voice 0.1.5-44 acceptance cannot be claimed from this image.
- Harness correction retained: the first terminal launch used obsolete `hyprctl dispatch exec` syntax, which this Hyprland rejected. The corrected test launched foot directly with the session environment and verified its actual window. This first attempt is not a product application failure. Initial SSH probes also lacked the GUI session environment; corrected probes imported only the needed installed session variables.

Reboot passed at the OS/filesystem level: `reboot-result.json` records a changed boot ID, preserved `macbook-vm-persistence` marker and system state `running`, with no failed system units. The wait after the reboot request took 59.23 host seconds; this is not a native boot benchmark. A second graphical user login was not repeated. The captured early reboot screen (`reboot-progress.png`) reports a failed encryption mapping for a non-LUKS test partition and inability to resume from `/dev/vda2`, then explicitly continues boot. These are retained warnings in this existing installed fixture, not a verified encrypted-install or hibernation result.

The test is complete; final container removal is verified in the evidence directory's `cleanup.txt`. No original base image was modified. Repository changes are limited to this handoff and its development-index link, left uncommitted for review. The system Git shim initially refused commands because of an unaccepted Xcode license; bundled Git provided status/log/worktree and documentation checks without changing the license or host configuration.

The post-reboot branded login screen was also visually verified in `reboot-greeter.png`. Documentation whitespace checks and the development-index link check passed; unchanged builds and acceptance suites were not rerun.

## Remaining gates before erasing macOS

1. Test a suitable existing USB environment or external-drive installation on the actual MacBook while retaining the internal macOS disk. Verify Apple Option-key boot and reboot from the selected external device.
2. Validate Intel HD 4000/GT 650M display routing and drivers, usable pointer, native 2880×1800 scaling, brightness and external display output. Virtio display success cannot establish these.
3. Validate Broadcom Wi-Fi, reconnect after suspend, Bluetooth, keyboard/Fn/backlight, trackpad/click/scroll and webcam.
4. Verify speakers, headphone jack and microphone, then separately verify current Maslow Voice/provider authentication, a heard response and agent delivery/result through the documented boundaries.
5. Verify lid suspend/resume, fan/cooling behavior, battery/charging and sustained native workload behavior. Do not infer these from a VM or CLI version output.
6. Verify the exact intended current software/package delivery and fresh-install app installation before the first supported OS update. This run did not install or update the OS, validate recovery/rollback, or test Retina scaling.
7. Confirm a restorable macOS/data backup and the intended installation disk before any later explicitly authorized erase.

Next action: use these results to prepare a non-destructive actual-MacBook hardware test. A VM pass is not authorization or sufficient evidence to erase its internal drive.
