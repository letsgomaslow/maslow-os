### Process-limit repair

Keep the other fixed outer limits; remove only outer `nproc`. Pin and bind the fixed verified root/package-owned util-linux `/usr/bin/prlimit` into the namespace read-only, applying its mount before read-only root finalization. Final command becomes fixed `prlimit --nproc=256:256 -- /usr/bin/APP-cli ...` after namespace creation and capability dropping. Verify the opened helper descriptor's type/ownership/mode/ELF identity, keep package verification, and fail closed on unavailable/untrusted helper or limit-setting failure. Do not expose caller-controlled helper arguments or relax the cap according to current desktop thread count. The fixed helper and app must inherit the existing filter, clean environment and descriptor closure.

The kernel limit counts tasks/threads for the real UID, with privileged exceptions; it is not simply a per-process child counter. Preserve the nonprivileged UID/capability behavior demonstrated here and verify enforcement in the supported kernel/install environment. The independent low-cap probe establishes plausibility of the ordering repair but does not replace a full-production-cap regression. See the primary [Linux getrlimit documentation](https://www.man7.org/linux/man-pages/man2/getrlimit.2.html).

### Why preflight plus link denial is insufficient for the unchanged claim

A useful conservative audit would start from the exact pinned output and state descriptors, recursively open components without following symlinks, inspect opened descriptors, reject every regular file with `st_nlink != 1`, reject special files, and fail closed on unreadable, changing or oversized trees. Reject nested mounts/aliases too; `st_dev` alone does not identify a bind mount. Rejecting all multiply linked files also rejects harmless links wholly inside output, which is preferable to claiming a race-free determination of all other names. Check state on every launch, not just first creation. Add x86_64 `link` and `linkat` to the existing ABI-checked filter, including `linkat(AT_EMPTY_PATH)` coverage; do not rely on native app flags or usual cross-mount `EXDEV` behavior.

That prevents static supplied hardlinks and creation of new hardlinks by the sandbox itself. It does not turn a host tree into an immutable set of writable inodes. Host-side replacement of a checked entry, insertion of an alias after enumeration, or a new outside hardlink to an already-open writable inode defeats the property. Root inode pinning, repeated audits, advisory Connect locks and inotify do not atomically interlock those operations with arbitrary app opens/writes. Existing session locks cover managed sessions, not other writers. Live GUI output and private state require the same analysis; “private” does not change Unix inode semantics.

An audit-only profile can be described accurately only with the explicit prerequisite that no outside process changes entries or creates links to any writable inode from the start of validation until every sandbox writer exits, and with refusal of unsafe initial contents. A shell/GUI promise or same-UID permission mode cannot enforce that prerequisite. This is a materially weaker supported-filesystem contract and must not silently replace the approved one. It could be a defense-in-depth patch while the acceptance gate stays held; it is not this review's recommended final boundary.

### Smallest coherent design for the existing filesystem contract

Keep the fixed app profiles, original canonical in-sandbox paths, read-only project and existing namespace/filter/lifecycle design. Change the two writable host binds, not the unrelated agent registry architecture:

1. Materialize output and private state into fresh private regular-file/directory trees. Never preserve hardlinks, symlinks, special files or nested mounts; use descriptor-relative no-follow reads and independent new inodes. Prefer sandbox-private storage without host directory entries available to concurrent ordinary writers; a mode-0700 staging directory owned by the same host UID is not, by itself, a stronger security principal. Bound bytes/files/depth and fail closed on unsupported trees. Existing host output/state must never be mounted writable into the app. A late source alias then supplies copied bytes at most; it does not supply the writable host inode. Do not mutate or “de-hardlink” the user's existing files during preflight.
2. Mount the materialized output at the approved canonical output path and copied state at `/craft-state`. Preserve reads of pre-existing exports and persistence of supported state through explicit import/publication. Discarding state every run or hiding existing output is a behavior change, not a transparent security fix. Deny `link`/`linkat` as defense in depth and keep unsupported object types out of publication.
3. Add a bounded trusted publisher outside the app sandbox. It accepts only relative artifact names beneath the pinned approved destination, validates components through directory descriptors, and publishes copied regular-file bytes into newly created temporary files followed by same-directory atomic rename. Never open an existing host target for truncate/write or preserve a supplied hardlink. Thus replacing an existing output hardlink changes that output directory entry, leaving its outside/project alias content intact. Handle symlink/nonregular destinations by explicit refusal or safe entry replacement, with the policy tested. Do the equivalent for persisted state. Do not give the app the publisher's destination FDs.
4. Use a narrow stdio MCP relay around the two fixed servers so publication completes before the corresponding saved-artifact success response reaches the agent. Session-exit-only copying is insufficient: clients keep MCP servers alive and immediately open reported canonical paths. The relay must preserve IDs/errors/cancellation, bound messages/work, serialize conflicting saves and return an error on failed publication. No new arbitrary command/mount/export-destination API is needed. Do not infer a trustworthy artifact path or completed writer merely from free-form app text. Inspect the actual pinned app tool schemas and completion behavior to define supported save operations; treat background writers, rename/delete behavior, multiple files, overwrites and cache reuse explicitly. If those require a generic filesystem synchronization product, defer that app instead of expanding this program.
5. A successful tool reply is not a general filesystem quiescence primitive. Capture a stable publication result or refuse/retry within a bound when app output changes during copying; hold success until host bytes exist and the relevant format/content check succeeds. Cancellation, parent death or export failure must not publish an unfinished artifact as successful. Preserve last committed state and clean abandoned staging safely. Avoid promising all-or-nothing publication of multiple files unless that transaction is actually implemented and tested.

Descriptor-relative operations, no-follow resolution and atomic leaf replacement address input-time path substitution and hardlink content writes; they do not make an actively hostile same-UID host harmless. In particular, moving an already-open destination directory changes where its inode is named. Define authority by the saved approved directory inode, check canonical-path identity before reporting success, and fail on detected root/ancestor conflicts. State explicitly that the host/agent can independently rename approved directories, directly alter results, inspect same-UID processes or rewrite user-owned configuration. Those actions are outside the app boundary. They do not excuse accepting pre-existing aliases, racing untrusted tree import, or following a swapped publication symlink. The existing public claim should remain about the confined native app, never confinement of its requesting agent or independently opened GUI.

This design is larger than adding two syscalls to the filter, but it removes the shared writable inode that causes the reproduced failure. A simple unsafe `copyFile` into existing paths or unrestricted recursive copy would merely move the vulnerability into Connect. Native descriptor-relative publication may require a carefully scoped helper; establish whether the existing implementation tools can provide the required semantics before committing to a repair scope.
