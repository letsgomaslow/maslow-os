## RETRO THEME STUDY: TWO THEMES SHIPPED, CRITICAL VIDEO-INTRO GPU HANG FOUND AND MITIGATED — October 19-20

A retro-UI exploration for the MacBook candidate (performance baseline first, then an HTML mockup comparing a 1984-style and a Mac OS 8/9 Platinum-style direction) led to two real, shipped themes and one serious, previously-unknown hardware-crash bug.

**Shipped to `main`:** `themes/maslow-platinum/` and `themes/maslow-1984/` (colors.toml + hyprland.lua + preview.png + backgrounds, [PR #23](https://github.com/letsgomaslow/maslow-os/pull/23) at `8cca004d`, previews [PR #25](https://github.com/letsgomaslow/maslow-os/pull/25) at `1ea35bba`, background assets [PR #26](https://github.com/letsgomaslow/maslow-os/pull/26) at `164c631a`). Platinum uses Maslow's real brand tokens (`branding/design-tokens.json`) for a silver-surface, brand-teal-bevel skin, achieved entirely through the existing `hyprland_active_border` gradient mechanism — no `shell.toml` or QML changes needed. 1984 is a stark black-and-white, zero-bevel skin; every ANSI terminal color deliberately collapses to black (a real, stated usability tradeoff for daily terminal use, not an oversight). A WCAG fix landed in the same PR: Platinum's original bevel-shadow color only hit 2.61:1 against one surface, under the 3:1 floor for UI borders — darkened to clear 3:1 everywhere.

**Two accessibility bugs found and fixed, neither obvious from the theme files themselves:** (1) `omarchy-theme-switcher`'s picker silently drops any theme with no `preview.png`/background image from its list — both new themes were invisible in Settings → Theme despite working correctly via `omarchy-theme-set` directly, fixed by PR #25. (2) `maslow-1984` rendered completely unreadable black-on-black bar text — root cause was neither font nor a bad color choice (traced and ruled out by a dedicated accessibility-audit subagent): with no `backgrounds/` directory, `~/.local/state/omarchy/current/background` resolved to a dangling symlink, and `omarchy-bar-text-color`'s `fallback()` echoes the theme's own foreground color unchanged whenever it has no real background to sample — for a pure-black-foreground theme, that's black text over `Background.qml`'s transparent root with nothing opaque behind it. Fixed by PR #26 (real static background images for both themes). The same audit swept WCAG contrast across all ~28 shipped themes: `muted`-on-background fails AA on 19 of them (pre-existing, both new themes are above the repo average, not the cause), and three pre-existing themes (`rose-pine`, `miasma`, `catppuccin-latte`) fail contrast even on their primary accent color — flagged for a separate session, not touched here.

**Critical, previously-unknown hardware bug: the theme picker's video-intro preparation hangs this MacBook's GPU hard.** `shell/plugins/image-picker/ImagePicker.qml`'s `introPrepareTimer` calls `omarchy-theme-bg-boot-intro --prepare-theme <name>` as the user navigates the picker, which hands the highlighted theme's `backgrounds/intros/*.mp4` straight to `owe intro-prepare` — the same OWE video-rendering path already confirmed (via the screensaver, see below) to crash this machine's nouveau/Kepler GPU outright (missing `msvld` hardware-decode firmware, real kernel-level `gr: TRAP`/`RT_WIDTH_OVERRUN` faults, not a soft stall). **20 of ~28 shipped themes ship a video intro** (`catppuccin`, `nord`, `hackerman`, `vantablack`, `lumon`, `retro-82`, and 14 others), so this was a standing landmine for any user of this picker on this hardware, unrelated to the two new themes. Directly reproduced twice by the user (full unrecoverable freeze, unresponsive to all input, did not recover even left overnight, required a power-button reboot both times) before the actual trigger was identified. **Mitigated, not code-fixed:** enabled the existing "Reduced Motion" accessibility toggle (`omarchy-hyprland-toggle reduced-motion on`, sets `animations:enabled=false` in Hyprland) plus the dedicated `~/.local/state/omarchy/toggles/background-intros-off` marker file directly — both independently verified by tracing `omarchy-theme-bg-boot-intro`'s own gate logic to abort before ever calling `owe`, then empirically confirmed clean (zero kernel GPU faults, compositor fully responsive) through an extended live navigation test across many themes including ones with video intros, landing repeatedly on `maslow-1984` itself with no issue. This is **device-local state, not a git change** — survives this machine's config but is not shipped to other installs; if this bug matters beyond this one MacBook, the real fix belongs in `ImagePicker.qml`/`omarchy-theme-bg-boot-intro` upstream of the theme-rules scope this session stayed within.

**A second, smaller GPU-cost finding in the same file, also device-local only:** every windowed carousel card in the picker gets its own `layer.enabled` + `MultiEffect` mask FBO; `previewRadius`'s cap was lowered device-locally from 16 to 4 as additional margin. Real but likely secondary to the video-intro bug above.

**Version-skew discovery, worth remembering for any future native QML work on this machine:** this machine's installed build is a divergent candidate snapshot, not `main` — and the divergence runs in **both directions** depending on the subsystem. The installed `shell/plugins/lock/Service.qml` expects fingerprint-unlock, video-wallpaper, and battery-aware power-saver properties on `LockView.qml` that don't exist on `main` at all (candidate ahead). The installed `shell/plugins/bar/BarModel.js` is missing tray-pinning/anchor-relative module-ordering functions that only exist on `main` (main ahead, opposite direction). Swapping either file wholesale from `main` broke the installed shell (confirmed: lock plugin failed to load entirely one way, bar module lookups threw `TypeError` the other way) until each fix was hand-re-applied as a narrow, self-contained diff directly against copies of the real installed files instead. Two such device-local patches remain live but **unmerged pending this reconciliation**: a lock-screen wallpaper-blur retune (`blurMax` 128→48, `blurMultiplier` 1.25→1.6, for this no-reclock GPU) and the `previewRadius` cap above — both tracked at `~/local-overrides/maslow-shell-2012-macbook/` on the machine itself (outside git, with its own README) and on the unmerged local branch `macbook-platinum-theme-20261019` (never pushed). A third such patch — a static Maslow brand-mark logo added to the top bar — was built, live-tested, then deliberately reverted and abandoned: `omadock`'s dock already has the real, official, functional Maslow logo (`Dock.qml`'s `DockIconButton`, the actual bundled brand glyph `U+E90B`, opens the main menu), so the bar addition was a redundant second logo, not a theme-rules-compliant change.

**Also landed:** [PR #24](https://github.com/letsgomaslow/maslow-os/pull/24) at `3d48c7ef` adds an explicit `AGENTS.md` rule never to push branches or open PRs against the public upstream `omacom/omarchy` fork, after doing exactly that by mistake once this session (`gh pr create` defaults to a fork's upstream parent unless `--repo` is passed explicitly) — caught immediately, closed within minutes, no review or merge happened there.

**Remaining gates:** the candidate/`main` lock and bar divergence above is unreconciled; native testing of further shell QML changes on this machine will keep hitting it until one side catches up to the other. The video-intro GPU bug's real fix (something safer than relying on Reduced Motion staying enabled) is not yet upstreamed. Next action: decide whether to pursue reconciling the candidate branch's lock-plugin features and `main`'s bar-plugin features, or keep treating this machine's `local-overrides/` directory as its permanent device-specific state.

## POST-FIX HEALTH SWEEP: FSTRIM AND SMART MONITORING ADDED, THREE FALSE ALARMS CORRECTED — October 19

A general health sweep after the MacBook work above found two real, general (non-hardware-specific) gaps and three things that looked like bugs but were not, each requiring a correction after initial over-claiming:

- **`fstrim.timer` enabled by default**, merged via [PR #22](https://github.com/letsgomaslow/maslow-os/pull/22) at `a7388c0e`. Stock systemd ships this disabled; nothing in this install's history ever opted in. Safe everywhere (`fstrim` skips mountpoints without discard support), a real long-term SSD benefit. Fresh installs get it via `install/config/enable-services.sh`; existing installs via a migration. Live-applied and confirmed correctly scheduled on its normal weekly cadence, no unexpected immediate trim run, and confirmed to survive a reboot cleanly.
- **`smartmontools` installed** on the MacBook so SSD health can actually be checked going forward (it was entirely missing — no way to query SMART data at all before this). SMART itself was also disabled at the drive level; enabled it, ran a self-test, recorded the baseline in `docs/macbook-development.md`'s hardware-facts section.
- **Recurring `tr` coredumps are not a bug.** Traced to `bin/omarchy-setup-ai-tool`'s `run_bounded_probe_with_timeout`, which deliberately wraps any AI-tool readiness probe in `ulimit -f 16` to bound output from a misbehaving external tool — the SIGXFSZ kill is the guard working as designed, not a defect. Separately, a visible Hub flicker and theme-looking activity one user saw traced to this exact mechanism: `bin/omarchy-setup-ai` (reachable from the Omarchy menu, and once automatically on first login if setup was never completed) opens `shell/plugins/maslow-ai-setup/Panel.qml`, which checks each supported AI tool's status sequentially through this same guard. No periodic timer triggers this — confirmed by checking every QML file in the shell — so the exact trigger moment couldn't be pinned down with certainty, but the mechanism itself is fully explained and benign.
- **The Broadcom `wl` driver's UBSAN array-bounds warning is very likely a false positive**, not a confirmed defect. The code allocates `sizeof(struct maclist) + MAXMULTILIST * ETHER_ADDR_LEN` bytes while the struct declares `ea[1]` — the classic pre-C99 flexible-array-member idiom, which trips static analysis against the declared type even though the real allocation and the loop's own bounds check are both correct. Decided not to file this as a bug after code inspection; `broadcom-wl-dkms` is Arch's own `extra`-repo package regardless, not something this project owns.
- **`gkr-pam: couldn't unlock the login keyring` at every login is deliberate architecture, not a misconfiguration.** `install/login/sddm.sh` intentionally strips the PAM `auth`-phase `pam_gnome_keyring.so` line to avoid creating a password-gated traditional login keyring; `install/user/default-keyring.sh` creates Omarchy's actual secrets store instead — a separate, deliberately unencrypted `Default_keyring` (`lock-on-idle=false`, `lock-after=false`) that apps like Chrome (`--password-store=gnome-libsecret`) genuinely use, confirmed by its file size having grown well past the script's own minimal template. The warning is SDDM's still-present `session`-phase PAM hook failing to unlock a conventional "login" keyring this architecture never creates — cosmetic noise, not a functional problem. Left alone: that same session hook is also what starts the keyring daemon Chrome actually depends on, so there's no way to silence just the cosmetic warning without risking the part that currently works.

Three corrections worth naming directly: the `tr` crash, the Broadcom warning, and the keyring warning were each initially reported as confirmed bugs from a surface-level pattern match (a coredump exists; a sanitizer fired; a scary-looking PAM error appears every login) before actually reading the owning code, and all three turned out to be working-as-designed once traced to source. Pattern-matching a symptom is not the same as a root cause.

## MACBOOK AC/BATTERY NOUVEAU PSTATE SWITCH — CLOSED OUT, MERGED — October 19

The [pstate switch handoff](handoffs/2026-10-19-macbook-nouveau-ac-pstate-switch.md) records a working, live-validated performance mitigation for the sluggishness root cause below: a udev rule forces nouveau pstate `0a` on real AC power and `07` on battery, merged to `main` via [PR #21](https://github.com/letsgomaslow/maslow-os/pull/21) at `041bf03a`. Research first confirmed nouveau has no true dynamic/load-based reclocking at all for this Kepler-generation chip — architectural, not a firmware gap — and that a third-party automatic-reclocking daemon carries a documented real lockup risk on this exact chip class, so a safer AC/battery-triggered static switch was built instead, deliberately never using the two pstates (`0e`/`0f`) that carry that risk. Live testing on the real hardware caught and fixed a real bug: the first attempt's battery target (writing nouveau's own `AC` pstate row label) is rejected outright, and the next guess (`auto`) is accepted but actually selects the riskiest `0f` level — neither does what its name suggests. Fixed to the explicit, confirmed-safe pstate `07`. The full automatic path — a real ACPI AC-adapter event firing the real installed udev rule — was end-to-end validated on the machine, not just manually invoked. Since `omarchy dev link` remains disabled on this build, the reviewed, committed scripts were placed manually at their real intended packaged location as a deliberate, flagged exception, pending a real package release of this branch.

## MACBOOK INTEL-IGPU FIX TESTED AND REVERTED — October 18

The [revert handoff](handoffs/2026-10-18-macbook-intel-igpu-fix-reverted.md) records that the nouveau-disable fix proposed below was implemented on branch `macbook-intel-igpu-display-fix` and live-tested on the actual MacBook. **It does not work on this hardware and must not be merged.** Directly confirmed via DRM connector enumeration: this MacBookPro10,1 hardwires its internal Retina panel to the discrete NVIDIA GPU only — Intel's `i915` has zero eDP connectors on this model, unlike later dual-GPU MacBooks where `apple_gmux` can mux the internal display. Disabling nouveau left the panel on an unaccelerated `simple-framebuffer` fallback with broken brightness controls, a regression rather than a fix. The machine was manually reverted and directly confirmed back to its known-good prior state (nouveau driving `eDP-1`, brightness/backlight controls working). The hardware-detector command (`omarchy-hw-macbookpro10-1`) is sound and reusable; the fix action itself is not. Real next step: investigate nouveau's own dynamic reclocking rather than any Intel-switch path, since none exists on this model.
